# kFarmAI 보조사업정보 공공데이터 설계

## 목적

보조사업 정보는 사용자가 지역, 대상, 분야별로 확인해야 할 공공정보를 찾도록 돕는 참고 정보로 운영한다. kFarmAI는 신청 가능 여부를 확정하지 않고, 공식 공고 확인 전 탐색 경로와 확인 포인트를 제공한다.

## 한 번에 가져오기 어려운 이유

- 보조사업은 중앙부처, 광역지자체, 기초지자체, 농업기술센터, 유관기관이 각각 공고한다.
- 같은 유형의 사업도 지역, 작물, 시설 규모, 자부담 조건, 신청기간, 대상 요건이 다를 수 있다.
- 공고문은 게시판, 첨부파일, 엑셀, PDF 등 다양한 형태로 제공되어 구조가 일정하지 않다.
- 신청 접수, 선정, 집행, 정산 정보가 서로 다른 시스템에 나뉘어 있을 수 있다.
- 공고가 수시로 바뀌므로 정적 데이터는 공식 확인 전 참고 정보로만 표시해야 한다.

## 활용 가능한 공공데이터 출처

- 농림축산식품부 농림축산식품분야 보조금 현황: 사업별 국고보조사업 현황과 지원자격, 지원내용 참고
- e나라도움 보조사업현황: 보조사업 현황, 공모사업, 수행단계별 현황 확인
- AgriX 농림사업정보시스템: 농림사업정보와 농림사업 시행지침 확인
- 지자체 농업기술센터 공고: 지역별 신청기간, 대상, 제출서류, 현장 조건 확인
- 스마트팜코리아: 스마트팜 교육, 지원사업, 관련 프로그램 확인

## 단기 구현

정적 JSON과 공식 링크 중심으로 구현한다.

- `data/subsidy_programs.json`에 대표 보조사업 확인 유형을 저장한다.
- 실제 개별 공고 URL이 확인된 항목만 `officialUrl`을 둔다.
- 개별 공고 URL이 없는 항목은 빈 링크를 만들지 않고 `공식 공고 확인 필요` 상태로 표시한다.
- 화면에서는 지역, 대상, 분야 필터를 제공한다.
- 모든 카드에 `신청 전 공식 공고를 확인하세요.` 문구를 표시한다.

## 중기 구현

공공데이터 파일과 API를 주기적으로 갱신하는 구조를 검토한다.

- 농림축산식품분야 보조금 현황 파일을 내려받아 유형별 인덱스로 정제한다.
- e나라도움 보조사업 현황과 공모사업 정보를 카테고리별로 연결한다.
- 지자체 공고는 우선 수동 검수 목록으로 관리하고, 안정화된 출처부터 자동 갱신한다.
- 갱신 실패 시 기존 정적 JSON과 공식 확인 안내를 fallback으로 유지한다.

## 장기 구현

지자체 공고 모니터링과 변경 감지를 검토한다.

- 지자체 농업기술센터 공고 게시판을 지역별로 수집 후보에 등록한다.
- 공고 제목, 신청기간, 대상, 첨부파일, 담당부서를 추출한다.
- 자동 수집 결과는 바로 확정 정보로 노출하지 않고 검수 상태를 표시한다.
- 동일 사업명의 연도별 공고를 연결해 신청기간 변화를 참고할 수 있게 한다.

## 공식 공고 확인 원칙

- kFarmAI의 보조사업 정보는 참고 정보이며 신청 확정 정보가 아니다.
- 신청기간, 대상, 제출서류, 자부담, 선정 기준은 공식 공고를 우선한다.
- 공식 URL이 확인되지 않은 항목은 링크처럼 표시하지 않는다.
- 반영 상태는 `공공데이터 기반 정리`, `공식 공고 확인 필요`, `확장 예정`으로 구분한다.
- 사용자가 다음 확인 경로로 이동할 수 있도록 농업정보 허브, 스마트팜, 시설재배, 농자재·관리, 재배가이드와 연결한다.

## 향후 API·크롤링 검토 계획

1. 농림축산식품분야 보조금 현황 파일을 정기 갱신 데이터로 검토한다.
2. e나라도움 보조사업현황과 공모사업 정보를 분야별 인덱스로 연결한다.
3. AgriX 농림사업 시행지침과 연도별 사업 정보를 확인 경로로 연결한다.
4. 지자체 농업기술센터 공고는 지역별 수집 후보 목록을 만들고, 변경 감지와 수동 검수 흐름을 분리한다.
5. API 키, secret, `.env.local` 내용은 문서와 프론트엔드 코드에 포함하지 않는다.

## 2026-10-29 수집 설계 v1

정책·지원 정보는 `수집 → 정규화 → 중복 제거 → 사람 검수 → 공개`의 다섯 단계로 운영한다. 기존 Daily 농업콘텐츠 자동화와 섞지 않고, 별도 REVIEW-only 파이프라인으로 둔다. 자동 수집 결과를 곧바로 Production에 게시하지 않는다.

### 1. 우선 수집원

기계 판독 우선순위는 `data/policy-support-sources.json`을 단일 레지스트리로 사용한다.

1. 보조금통합포털 OpenAPI의 `공모사업`, `보조사업현황`, `내역사업현황`
2. 농림축산식품 공공데이터 포털의 시행지침서·보조금 현황 공식 파일
3. AgriX 시행지침서의 공식 확인 링크
4. 허용목록에 등록하고 이용조건을 검토한 지자체·농업기술센터 공고

OpenAPI의 실제 base URL과 요청 파라미터는 발급된 명세서를 확인한 뒤에만 코드에 반영한다. 화면 주소를 API 주소로 추정하거나 비공개 게시판을 크롤링하지 않는다.

공공데이터포털의 공식 카탈로그 `15156853`(국고보조금 공모사업 상세)은 확인했다. REST/JSON·XML, 개발·운영 자동승인 데이터셋이지만, 실제 오퍼레이션 URL과 파라미터는 활용신청 후 제공되는 명세로 확정해야 한다. 따라서 레지스트리는 `verified_catalog_pending_operation_spec`으로 두며 URL을 추정해 넣지 않는다.

### 2. 서버 경계

- 프론트엔드는 외부 공공 API를 직접 호출하지 않는다.
- Worker에는 향후 `GET /api/policy-support` 읽기 전용 경로를 추가한다.
- 인증정보는 Worker secret `BOJO_OPEN_API_KEY` 같은 별칭으로만 참조한다.
- 응답 캐시는 성공 6시간, 오류는 `no-store`로 둔다.
- 공급자 오류 시 마지막 `approved` 스냅샷만 사용하고, 기준일을 숨기지 않는다.
- Supabase Auth, RLS, Storage 정책은 이 단계에서 변경하지 않는다.

### 3. 정규화 계약

공개 후보는 최소한 아래 필드를 가져야 한다.

```json
{
  "sourceId": "bojo-open-api",
  "externalId": "공급자 원문 식별자",
  "title": "공모·지원사업명",
  "summary": "사용자용 1~2문장 요약",
  "region": ["전국"],
  "targets": ["농업인"],
  "categories": ["시설원예"],
  "agency": "시행기관",
  "applicationStart": "2026-01-01",
  "applicationEnd": "2026-02-01",
  "publishedAt": "2026-01-01",
  "updatedAt": "2026-01-01T00:00:00+09:00",
  "officialUrl": "공식 상세 공고 URL",
  "sourceHash": "원문 정규화 SHA-256",
  "reviewStatus": "pending"
}
```

날짜, 공식 URL, 원문 식별자 중 하나라도 검증할 수 없으면 `approved`로 승격하지 않는다. 신청자격과 지원금액은 원문에 명시된 경우에만 표시한다.

### 4. 중복·변경 감지

- 1차 키: `sourceId + externalId`
- 2차 키: 정규화한 `title + agency + applicationEnd`
- 변경 감지: 원문 핵심 필드의 `sourceHash`
- 같은 사업의 수정 공고는 기존 항목을 덮어쓰지 않고 revision으로 연결한다.
- 마감일이 지난 공고는 `closed`, 변경·취소 공고는 `changed`로 분리한다.

### 5. 검수와 공개

- `pending`: 자동 수집 직후, 비공개
- `review`: 필수 필드와 공식 URL 검증 대기, 비공개
- `approved`: Production 표시 가능
- `rejected`: 비농업·중복·출처 불명
- `expired`: 마감 경과

공개 화면은 `approved`만 읽는다. 카드에는 제목, 지역, 대상, 신청기간, 시행기관만 우선 표시하고, 상세 설명은 1~2문장으로 제한한다. 신청 여부는 확정하지 않고 공식 공고 버튼을 제공한다.

### 6. 단계별 구현 순서

1. 소스 레지스트리와 JSON Schema 검증
2. 보조금통합포털 OpenAPI 명세·키 확인
3. 로컬 fixture 기반 정규화기와 중복 제거 테스트
4. Preview Worker의 읽기 전용 `/api/policy-support`
5. REVIEW 산출물과 승인된 정적 스냅샷 생성
6. `subsidy-calendar.html`에서 승인 스냅샷 우선 표시
7. 운영 승인 후 스케줄 활성화

Production 자동수집 스케줄과 Worker secret 등록은 별도 승인 항목이다.

### 7. 구현된 REVIEW-only 기반

- `automation/policy_support_refresh.py`: 공식 API 응답 JSON을 정규화하고 중복을 제거한다. 외부 호출과 공개 동작은 하지 않는다.
- `data/schemas/policy-support-review.schema.json`: 검수 산출물 계약이다.
- 새 후보는 항상 `pending`이며 보조금통합포털의 HTTPS 상세 URL, 공급자 원문 식별자, 제목이 없으면 후보에서 제외한다. 다른 공급자는 URL 허용목록과 필드 매핑을 별도로 검증한 뒤 추가한다.
- 해시는 정규화한 핵심 필드를 SHA-256으로 계산해 수정 공고를 감지한다.
- 실제 수집 스케줄, Worker secret, `/api/policy-support`, Production 공개는 아직 활성화하지 않는다.

다음 구현은 활용신청으로 발급받은 공식 오퍼레이션 명세와 `BOJO_OPEN_API_KEY`를 Preview Worker에 등록한 뒤 진행한다. Preview에서는 원문 응답을 REVIEW 산출물로만 보관하고, 사람이 `approved`로 전환한 스냅샷만 공개 데이터에 합친다.
