# kFarmAI 커뮤니티 댓글 사진첨부 설계

## 1. 문서 목적

이 문서는 kFarmAI 커뮤니티에서 네이버카페/블로그처럼 댓글, 답글, 비밀댓글, 비밀댓글 답글에도 사진첨부 등록/수정/삭제를 지원하기 위한 장기 설계를 정리한다.

이번 문서는 설계 문서이며, 코드 수정, DB 스키마 변경, Supabase SQL 실행, Storage bucket 생성은 포함하지 않는다.

## 2. 현재 커뮤니티 기능 상태

현재 커뮤니티는 게시글 중심 사진첨부 기능이 먼저 구현되어 있다.

- 게시글 등록: 지원
- 게시글 수정: 지원
- 게시글 삭제: 지원
- 게시글 사진첨부 등록: 지원
- 게시글 사진첨부 수정: 지원
- 게시글 기존 사진 유지: 지원
- 댓글: 지원
- 답글: 지원
- 비밀댓글: 지원
- 비밀댓글 답글: 지원

현재 댓글/답글/비밀댓글에는 사진첨부 기능이 붙어 있지 않다. 댓글 사진첨부는 게시글 사진첨부보다 권한과 보안 설계가 더 까다롭다. 특히 비밀댓글 사진은 공개 URL 방식으로 처리하면 보안 요구에 맞지 않을 수 있다.

## 3. 구현 목표

최종 목표는 아래 범위를 순차적으로 지원하는 것이다.

- 일반 댓글 사진첨부 등록
- 일반 댓글 사진첨부 수정
- 일반 댓글 사진첨부 삭제
- 일반 답글 사진첨부 등록
- 일반 답글 사진첨부 수정
- 일반 답글 사진첨부 삭제
- 비밀댓글 사진첨부 등록
- 비밀댓글 사진첨부 수정
- 비밀댓글 사진첨부 삭제
- 비밀댓글 답글 사진첨부 등록
- 비밀댓글 답글 사진첨부 수정
- 비밀댓글 답글 사진첨부 삭제
- Android 사진첨부 대응
- iPhone 사진첨부 대응

사진첨부는 진단 근거를 확정하는 용도가 아니라, 커뮤니티 사용자가 증상이나 상황을 설명하기 위한 참고자료로 취급한다.

## 4. DB 설계 후보 A: comments.image_urls

comments 테이블에 이미지 URL 배열 컬럼을 추가하는 방식이다.

예시:

```sql
alter table public.comments
add column image_urls text[];
```

또는 JSON 구조가 필요하면 다음 방식도 가능하다.

```sql
alter table public.comments
add column image_urls jsonb;
```

### 장점

- 구현이 단순하다.
- 기존 comments 조회 로직에 이미지를 함께 붙이기 쉽다.
- 댓글 등록/수정 payload에 `image_urls`만 추가하면 초기 구현이 가능하다.
- 게시글의 `posts.image_urls` 처리 방식과 비슷하게 맞출 수 있다.

### 단점

- 이미지별 메타데이터 관리가 어렵다.
- 이미지 삭제, 숨김, 신고 처리 이력이 약하다.
- Storage 고아 파일 정리가 어렵다.
- 비밀댓글 이미지 권한을 URL 배열만으로 제어하기 어렵다.
- 이미지별 업로드 실패/삭제 상태를 추적하기 어렵다.

## 5. DB 설계 후보 B: comment_images 별도 테이블

댓글 이미지를 별도 테이블로 관리하는 방식이다.

예시 테이블:

```text
comment_images
- id
- comment_id
- post_id
- user_id
- storage_provider
- bucket
- path
- public_url
- size_bytes
- width
- height
- created_at
```

추가로 장기 운영을 고려하면 아래 필드도 검토할 수 있다.

```text
- mime_type
- original_name
- is_secret
- deleted_at
- hidden_at
- hidden_by
- report_count
```

### 장점

- 이미지별 관리가 쉽다.
- 삭제/숨김/신고/고아 파일 정리 구조를 만들기 좋다.
- Storage path와 DB 레코드를 1:1로 추적할 수 있다.
- 관리자 기능과 연결하기 쉽다.
- 비밀댓글 이미지를 별도 권한 정책으로 분리하기 좋다.

### 단점

- 구현이 복잡하다.
- 댓글 조회 시 join 또는 별도 조회가 필요하다.
- RLS 정책이 더 많아진다.
- 등록/수정/삭제 흐름에서 트랜잭션성 처리가 필요할 수 있다.

## 6. 추천안

초기 구현은 `comments.image_urls` 방식으로 시작할 수 있다.

단, 비밀댓글 사진첨부까지 고려하면 장기적으로는 `comment_images` 별도 테이블 방식을 권장한다.

추천 전략:

1. 일반 댓글과 일반 답글은 `comments.image_urls`로 빠르게 MVP 구현
2. 비밀댓글 사진첨부는 바로 붙이지 않고 private 이미지 설계를 먼저 확정
3. 운영 기능, 신고 기능, 관리자 삭제가 필요해지는 시점에 `comment_images` 테이블로 확장

비밀댓글까지 처음부터 안전하게 구현하려면 `comment_images` + private bucket + signed URL 또는 Worker/API 권한 확인 구조를 우선 검토한다.

## 7. Storage 설계

### bucket 후보

```text
comment-images
```

### 경로 규칙

```text
comment-images/{userId}/{commentId}/{fileName}
```

예시:

```text
comment-images/USER_ID/COMMENT_ID/20260707-a8f3k2.jpg
```

### 파일명 규칙

- 원본 파일명을 그대로 쓰지 않는다.
- 한글, 공백, 특수문자를 제거하거나 사용하지 않는다.
- 확장자는 검증 후 소문자로 저장한다.
- 중복 방지를 위해 시간값과 랜덤 문자열을 사용한다.

예시:

```js
const safeName = `${Date.now()}-${Math.random().toString(36).slice(2)}.${ext}`;
```

## 8. RLS 정책 방향

RLS는 댓글 작성자, 게시글 작성자, 비밀댓글 여부를 함께 고려해야 한다.

필요한 원칙:

- 댓글 작성자만 본인 댓글 이미지 업로드 가능
- 댓글 작성자만 본인 댓글 이미지 수정 가능
- 댓글 작성자만 본인 댓글 이미지 삭제 가능
- 공개 댓글 이미지는 게시글 조회 가능 사용자에게 표시 가능
- 비밀댓글 이미지는 작성자와 게시글 작성자만 조회 가능
- 관리자는 신고/부적절 이미지 숨김 가능

일반 댓글만 public bucket으로 시작할 수는 있지만, 비밀댓글은 public bucket과 public URL 방식이 맞지 않을 수 있다.

## 9. 비밀댓글 사진첨부 주의점

비밀댓글 사진첨부는 일반 댓글 사진첨부보다 늦게 구현하는 것이 안전하다.

주의할 점:

- public URL 이미지는 URL을 아는 사람이 직접 접근할 수 있다.
- 비밀댓글 본문은 숨겨도 이미지 URL이 노출되면 의미가 약해진다.
- 비밀댓글 이미지는 private bucket을 사용해야 할 가능성이 높다.
- private bucket을 쓰면 signed URL 발급이 필요하다.
- signed URL은 만료 시간이 있으므로 재조회/갱신 흐름이 필요하다.
- 프론트에서 권한 없는 사용자가 signed URL을 받을 수 없도록 API 또는 RLS 설계가 필요하다.

추천 방식:

```text
일반 댓글 이미지: public bucket 또는 공개 조회 정책 가능
비밀댓글 이미지: private bucket + 권한 확인 후 signed URL 발급
```

비밀댓글 이미지까지 안전하게 처리하려면 Supabase Edge Function 또는 Worker endpoint에서 권한을 확인한 뒤 signed URL을 내려주는 구조를 검토한다.

## 10. 구현 우선순위

1. 일반 댓글 사진첨부 등록
2. 일반 답글 사진첨부 등록
3. 댓글/답글 사진 수정
4. 댓글/답글 사진 삭제
5. 비밀댓글 사진첨부 보안 설계 확정
6. 비밀댓글 private 이미지 처리
7. 관리자 삭제/숨김
8. 고아 이미지 정리 배치 또는 관리 도구

1단계와 2단계는 현재 게시글 사진첨부 로직의 파일 검증, 업로드, `image_urls` 정규화 방식을 재사용할 수 있다.

## 11. 모바일 대응

댓글 사진첨부는 모바일 사용 비중이 높으므로 Android/iPhone 대응을 처음부터 포함해야 한다.

확인할 항목:

- iPhone HEIC/HEIF
- Safari에서 `file.type`이 빈 값인 경우
- 카카오톡/인스타그램 등 인앱브라우저 파일 선택 차이
- 10MB 초과 파일 안내
- 느린 네트워크에서 업로드 중복 클릭 방지
- 업로드 실패 후 버튼 disabled 복구
- 업로드 전 리사이즈/압축 검토
- 업로드 중 진행 상태 표시
- 사진 선택 직후 파일 형식/용량 안내

권장 안내 문구:

```text
아이폰 고효율 사진 형식입니다. 일부 브라우저에서 표시가 어려울 수 있습니다. 실패하면 스크린샷 또는 JPG 사진으로 다시 시도해주세요.
```

```text
사진 용량이 너무 큽니다. 10MB 이하 사진을 선택해주세요.
```

```text
카카오톡 안에서 열린 화면이면 Safari에서 직접 열고 다시 시도해주세요.
```

## 12. 관리자 기능 연계

댓글 사진첨부가 들어가면 관리자 기능과 연결해야 한다.

필요 기능:

- 부적절 이미지 삭제
- 신고 이미지 확인
- 비밀댓글 이미지 권한 확인
- Storage 사용량 모니터링
- 고아 이미지 정리
- 특정 댓글 이미지 숨김
- 삭제된 댓글의 이미지 보존/삭제 정책

관리자 페이지에서 바로 Storage 파일을 삭제할지, 우선 DB에서 숨김 처리 후 나중에 정리할지 정책을 정해야 한다.

권장 초기 정책:

```text
사용자 화면에서는 숨김 처리
Storage 실제 삭제는 관리자 확인 후 별도 처리
```

- Storage public/private 정책 결정
- `comments.image_urls` 방식 vs `comment_images` 별도 테이블 결정
- 일반 댓글과 비밀댓글을 같은 bucket으로 처리할지 분리할지 결정
- signed URL 필요 여부 결정
- UI 범위 결정
- 사진 수정 UI 범위 결정
- Storage 실제 파일 삭제 여부 결정
- Android 테스트 계획
- iPhone Safari 테스트 계획
- 인앱브라우저 안내 문구 결정

## 14. 향후 추천 구현 순서

### 1단계: 일반 댓글 사진첨부

- 일반 댓글 등록 폼에 사진 선택 추가
- 최대 3장 등 제한 설정
- 파일 형식/용량 안내
- Storage upload
- `comments.image_urls` 저장
- 댓글 렌더링 시 이미지 표시

### 2단계: 일반 답글 사진첨부

- 답글 폼에 사진 선택 추가
- 답글 댓글 레코드에 `image_urls` 저장
- 부모 댓글 UI와 겹치지 않게 이미지 표시

### 3단계: 댓글/답글 사진 수정/삭제

- 기존 이미지 유지
- 이미지 제거 UI
- 새 이미지 추가
- Storage 실제 파일 삭제는 보류 가능

### 4단계: 비밀댓글 사진첨부 설계 확정

- public URL 사용 금지 여부 결정
- private bucket 사용 여부 결정
- signed URL 발급 방식 결정
- 게시글 작성자/댓글 작성자 권한 확인 방식 결정

### 5단계: 비밀댓글 private 이미지 처리

- private bucket 업로드
- 권한 확인 후 signed URL 제공
- URL 만료와 재조회 처리

### 6단계: 관리자 삭제/숨김

- 이미지 신고/숨김
- 부적절 이미지 관리자 삭제
- 고아 이미지 정리
- Storage 사용량 관리

## 15. 안전 문구 원칙

댓글 이미지는 사용자 커뮤니티 참고자료다.

사용하지 않을 표현:

- 정확한 진단
- 최종 처방
- 추천 농약
- 이 농약을 쓰세요
- 오늘 방제하세요

사용할 표현:

- 참고 이미지
- 증상 확인용 참고자료
- 추가 확인 포인트
- 공공정보 확인
- 안전사용기준 확인

## 16. 결론

댓글 사진첨부는 사용자 경험을 크게 개선할 수 있지만, 비밀댓글과 이미지 접근 권한 때문에 게시글 사진첨부보다 보안 설계가 중요하다.

초기에는 일반 댓글/답글 사진첨부를 `comments.image_urls` 방식으로 가볍게 시작할 수 있다. 다만 비밀댓글 사진첨부는 public URL 방식으로 바로 구현하지 말고, private bucket과 signed URL 또는 권한 확인 API를 설계한 뒤 단계적으로 적용하는 것이 안전하다.
