# KFarmAI 정책·지원 API 서비스 설계 v1 — 2026-10-29

## 범위와 현재 상태

농업인이 지역·대상·분야에 맞는 **공식 지원사업 공고를 찾고 원문으로 이동**하도록 한다. 기존 `subsidy-calendar.html`의 정적 `data/subsidy_programs.json`은 탐색 참고 유형이며 실제 접수 중인 공고와 혼동하지 않게 분리한다. 이 문서는 API 키가 없는 단계의 제품·데이터 계약이다. 실제 공고 수집, 공개 API, 자동 갱신은 활성화하지 않는다.

공식 출처: [보조금통합포털 OpenAPI 안내](https://www.bojo.go.kr/ga/retrieveOpnApi.do), [공공데이터포털 국고보조금 공모사업 상세](https://www.data.go.kr/data/15156853/openapi.do). 포털은 `공모사업`, `보조사업현황`, `내역사업현황`을 안내한다. 개별 오퍼레이션 URL·요청 파라미터·응답 필드명은 활용신청 후 발급된 명세와 샘플 응답으로 확정한다. 현재 정규화기의 별칭은 **fixture 가정**이며 공급자 계약으로 간주하지 않는다.

## 서비스에 필요한 공고

| 우선 | 포함 | 화면 분류 | 수집 판단 |
| --- | --- | --- | --- |
| P0 | 농업인·청년농·농업법인·귀농인의 영농정착, 시설원예·스마트팜, 농기계, 친환경, 유통·가공, 교육·재배기술 | 실제 신청 공고 | 농업 관련성, 공식 상세 URL, 식별자와 접수기간 확인 후 검수 후보 |
| P1 | 농자재·에너지 절감·재해 예방 등 농업 현장과 직접 관련된 공고 | 실제 신청 공고 | 대상과 지원 내용 원문 확인 후 후보 |
| 보류 | 농업과 무관한 일반 보조금, 집행·정산 통계, 수혜자 명단, 종료된 과거 사업 | 공개 목록 제외 | 집행 현황은 공고 대용으로 게시하지 않음 |

키워드 일치만으로 자동 공개하지 않는다. `농업`이라는 말이 없더라도 시설원예와 연관된 사업은 검수 후보가 될 수 있다. 반대로 `스마트`만 포함된 비농업 사업은 제외한다. 공급자 필드에 지원대상·지역·분야가 없으면 추측해서 채우지 않고 `미확인`으로 검수한다. 국고 공고에 없는 **지자체·농업기술센터의 지역 공고**는 허용된 공식 출처를 별도로 등록해야 전국 서비스가 된다.

## 화면 계약 (`subsidy-calendar.html`)

1. 상단 제목 `정책·지원`, 한 줄 출처·기준일. 공고 목록과 현재의 `지원 유형 참고`를 별도 영역으로 두고 건수를 합산하지 않는다.
2. 기본 목록은 검수 승인된 **접수 중 공고**. 마감 임박 순으로 정렬하고 공고일을 보조 기준으로 사용한다. `예정`, `마감`은 상태 선택으로 따로 볼 수 있게 한다. 시작/종료일 또는 상태가 미확인인 건은 `접수 중`이라고 단정하지 않는다.
3. 필터: 지역(전국 공고 포함), 대상, 분야, 접수 상태. 모바일에서는 2행 이하의 간결한 선택 UI. 위치 권한은 요구하지 않는다. 선택한 지역에 전국 공고를 함께 보여준다.
4. 목록 한 건은 `상태 배지 · 제목 · 시행기관 · 대상/지역 · 신청기간`을 1~2줄 중심으로 표기한다. 카드 전체나 `공식 공고` 버튼을 누르면 검증된 공식 상세 URL을 새 창으로 연다. 긴 사업 설명과 중복 안내문은 목록에 두지 않는다.
5. 상세 화면을 만들 경우 `지원내용`, `자격`, `자부담/지원액`, `신청방법·제출서류`는 원문에 명시된 것만 표시하고 항목별 미확인은 생략한다. 자격 충족·선정 가능성을 판정하지 않는다. 출처, 공고일, 수정일, 수집 시각, 공식 URL은 구분한다.
6. 데이터가 비었을 때 `조건에 맞는 확인된 공고가 없습니다.`를 보여주고 필터 초기화와 공식 공고 검색을 제공한다. API 실패 시 마지막 **승인 스냅샷**과 기준일을 보여주거나, 승인본이 없으면 안내만 보여준다. 미검수 자료나 오래된 정적 유형을 최신 공고처럼 대체하지 않는다.

## 수집·검수·공개 계약

`공모사업`을 공고 후보의 주 공급원으로 사용한다. `보조사업현황`과 `내역사업현황`은 명세가 공고 식별자와의 안전한 연결을 제공할 때만 보충한다. 연결 키가 없으면 사업명 유사성만으로 결합하지 않는다.

| 단계 | 입력/출력 | 통과 조건 |
| --- | --- | --- |
| 수집 | 공급자 원문, 공급자 ID, 수집시각 | 서버에서만 키 사용; 페이지네이션·오류·호출량 기록 |
| 정규화 | `sourceId`, `externalId`, 제목, 지역/대상/분야, 기관, 신청 시작·종료일, 공고/수정일, 공식 URL, 원문 hash | 공식 명세로 필드 매핑; 날짜는 실제 달력일·시작≤종료; HTTPS 공식 상세 링크 검증 |
| 선별·중복 | 농업 관련 후보 및 수정 이력 | ID 우선, 기관·제목·기간 보조; hash 변화는 revision; 중복 출처 연결 |
| 검수 | `pending → approved/rejected`, 검수자·시각·원문 근거 | 신청기간·자격·공식 링크 확인; 수정·취소 공고 재검수 |
| 공개 | `approved` 스냅샷 또는 읽기 전용 API | 공개본만 제공; 종료일 경과는 상태 재계산; 수집 시각과 원문 기준일 별도 표기 |

`공고일`, `API 수집시각`, `우리 사이트 마지막 갱신시각`은 다른 값이다. 화면의 `업데이트`를 수집시각 하나로 오해시키지 않는다. 승인된 스냅샷은 원문 URL과 hash, 검수 근거를 남긴다. 지원금·자부담·신청자격은 원문 필드가 검증될 때만 표기한다.

현재 `automation/policy_support_refresh.py`는 로컬 fixture를 REVIEW 산출물로 정규화하는 단계이며 실제 호출이나 공개를 하지 않는다. `data/schemas/policy-support-review.schema.json`은 미검수 산출물 계약이다. 공개본에는 별도 `approved` 계약과 `reviewedAt`, `reviewer`, `sourcePublishedAt`, `collectedAt`, `snapshotAt`이 필요하다. 공개 API의 응답은 키와 원문 내 개인정보·불필요한 사업자 정보를 포함하지 않는다. 기존 Supabase Auth/RLS, Storage Gateway, KB 원문/hash는 변경하지 않는다.

## 키를 받은 뒤 구현 순서

1. 활용신청 명세와 비식별 샘플 응답으로 오퍼레이션 URL, 필드, 페이지네이션, 갱신주기·호출한도·이용조건을 확인한다. 명세가 없는 필드는 제품 계약에서 `미확인` 처리한다.
2. Preview Worker의 secret에 키를 등록한다. 키를 저장소·브라우저·Actions 로그·문서에 기록하지 않는다. 수집 실행은 REVIEW 전용으로 제한한다.
3. 실제 샘플로 매핑·농업 관련성·중복·날짜·변경 공고 테스트를 추가한다. 공급자 오류·빈 응답·429·키 오류에서 마지막 승인본만 유지한다.
4. `approved` 공개 계약과 읽기 전용 `GET /api/policy-support`를 Preview에 구현한다. `subsidy-calendar.html`은 승인 공고와 정적 참고 유형을 구분해 표시한다.
5. 390px 화면, 필터, 공식 링크, 만료/수정, 접근성, XSS·URL·키 유출, 기존 페이지 회귀를 검증한다. 실제 Galaxy 화면은 별도로 확인한다.
6. 검수 운영자와 갱신 시각을 정하고 일정·Production 활성화를 별도 승인 후 진행한다. 수집 빈도는 제공기관 주기와 한도를 확인한 다음 확정한다.

## 현재 결정이 필요한 운영 항목

- 키·공식 오퍼레이션 명세 및 비식별 응답 예시의 전달 방법(키 자체는 채팅/커밋에 붙이지 않고 Preview Worker secret으로 등록).
- `approved`로 승격하는 검수 담당자 및 정정·철회 처리 담당자.
- 1차 지역 범위: 전국 공고와 모든 시도, 지자체 상세 공고는 검증된 출처부터 추가.

**현 상태:** 화면과 데이터 계약 설계 완료. 공급자 응답 기반 필드 확정·실제 수집·자동 갱신·Production 공개는 미완료.

## Preview 구현 — 키 없이 검증 가능

- `data/policy-support-approved.json`: 승인 항목 0건인 공개용 정적 스냅샷. 승인 공고가 없을 때의 정직한 기본 화면이다. 수집 후보를 이 파일에 직접 합치지 않는다.
- `data/schemas/policy-support-approved.schema.json`: 공개 항목의 최소 계약. `reviewStatus=approved`, 공식 URL, 검수시각, 신청기간, 원문 hash가 필요하다. 검수자 식별자는 공개하지 않고 내부 검수 이력에만 둔다.
- `static/js/policy-support.js`: 승인본만 읽고 KST 기준 접수 상태를 계산한다. 필수 필드/URL/날짜 오류가 있으면 스냅샷 전체를 거부한다. 지역 필터에는 전국 공고를 함께 포함한다.
- `subsidy-calendar.html`: 승인 공고와 기존 정적 `지원 유형 참고`를 분리하고, 샘플 화면에서도 신청 링크를 막는다. 실제 공고가 아닌 시험 자료는 localhost에서 `?policyPreview=sample`로만 확인하며 선명하게 표시한다.
- `tests/fixtures/policy-support/approved.sample.json`: 화면 시험용 가상 사례. Production 승인 데이터가 아니다.

실제 OpenAPI 키와 공식 응답 명세를 받기 전에는 프론트엔드의 이 스냅샷에 공고를 임의로 넣지 않는다. 승인본 생성기, 운영 검수 화면, Worker API, 자동 갱신 일정은 후속 단계이다.
